Part 1: README

1.1 Project introduction

The Email Intelligence Platform lets individuals, businesses, sales professionals, recruiters, marketers, developers and organizations discover publicly available professional email addresses, verify email deliverability signals, analyze companies and professional contacts, process email lists in bulk, and integrate through APIs. [Confirmed]

The platform is intended to be publicly accessible globally, subject to applicable laws, technical availability and supported deployment regions. [Confirmed]

1.2 Three core engines

Engine

Role

Works without AI?

Discovers publicly listed business emails from company pages and permitted public professional pages. Tracks source and method for each result.

Yes

Collects technical evidence (syntax, DNS, MX, SMTP, catch-all) and applies deterministic classification rules.

Yes (AI is never involved)

1.3 Goals

Provide a free, professional, reliable Find / Verify / Enrich experience.

Be honest about accuracy: never promise 100% verification and never label inconclusive results as verified.

Be safe by design: SSRF protection, public-only discovery, abuse controls, audit logging.

Be implementable: detailed enough for a development team or AI coding agent.

1.4 Technology baseline (summary)

[Proposed, per master prompt baseline] Python 3.12 or compatible, Django 5.2 LTS, Django REST Framework, PostgreSQL, Redis, Celery (and Celery Beat for scheduled work), Gunicorn, Django Templates with HTML/CSS/JavaScript. Full table in Part 3.

1.5 Setup overview

Detailed setup is in Part 13. In summary, a developer will: clone the repository, copy .env.example to .env and fill values, start PostgreSQL and Redis (via Docker Compose), run Django migrations, start the Django web process, a Celery worker and Celery Beat, and run the test suite with pytest.

[Assumption] Windows and Linux developer machines are both possible; Docker Compose is the recommended common path.

Part 2: Product Requirements Document (PRD)

2.1 Problem statement

Finding and checking business email addresses is usually split across several tools, many of them paid, and results are often presented with more certainty than the underlying evidence supports. Users need a single free platform that finds publicly listed emails, shows where each came from, and verifies technical deliverability signals honestly.

2.2 Product vision

A trustworthy, evidence-based email discovery and verification platform where every result explains its source and its evidence level.

2.5 User stories

As a visitor, I can register, verify my email and log in so that my history is saved.

As a user, I can submit a company website and see publicly listed emails with their source pages.

As a user, I can search a person by profile URL or by name and company and see discovered and inferred candidates labeled separately.

As a user, I can verify one email and see the status, reason codes and evidence.

As a user, I can upload a CSV or XLSX, choose the email column, monitor progress and export results.

As a developer, I can create an API key, see it once, and call the public API with documented schemas.

As an admin, I can monitor jobs, workers, queues and abuse signals, with all sensitive access audited.

3.7 Background processing summary

Details are in Part 11 and Part 13. Tasks are chunked, idempotent, retried with exponential backoff, and tracked by status in the database. The initial deployment has finite capacity; scaling is by adding workers, queues and database resources.

3.8 Scalability path [Proposed]

Single host: web, one or more workers, PostgreSQL, Redis.

Separate worker hosts; separate queues for crawl and verification workloads.

Managed PostgreSQL and Redis; object storage for exports and uploads.

Read replicas or caching only if measured need appears.

Extract a component into a service only if a measured requirement justifies it.

4.4 Ownership and authorization

Every user-visible record carries owner_id. All queries in views and API endpoints are filtered by the authenticated owner. Administrators can read user records only through the audited admin process (Part 8). DomainRecord is shared, non-personal cache data.

4.5 Duplicate prevention and transactions

Unique constraints listed above prevent duplicate emails per job, duplicate rows per bulk job, and duplicate chunks.

Chunk processing writes results and marks the chunk done inside one database transaction; a retried chunk skips records already in a final state.

Idempotency-Key on public API creation endpoints maps to a unique constraint per owner.

Job status transitions are performed with conditional updates to prevent two workers from taking the same chunk.

4.6 Data retention and user deletion

Users control retention for their history within platform-defined bounds [Open: bounds].

Account deletion removes or anonymizes the user's records; audit entries may be retained in minimized form [Validate: legal basis].

Uploaded bulk files are not kept longer than needed to process the job [Proposed].

API key hashes are deleted with the account; request logs follow retention policy.

Part 5: API Specification

5.1 Architecture

Two layers [Confirmed]: Internal API under /internal/api/ for the Django-template frontend (session + CSRF) and Public API under /api/v1/ for external developers (API key). They share services, not views.

5.2 Public API authentication and key lifecycle

Header: Authorization: Api-Key <full key> [Proposed].

Keys are generated with a cryptographically secure random source (Python secrets). Format: a short visible prefix plus a long random secret.

Only a hash of the key and the prefix are stored. The full key is shown once at creation or regeneration.

Because keys are long random values, a fast cryptographic hash is acceptable for storage; passwords use Argon2 [Proposed].

Revocation is immediate. Regeneration revokes the old key and issues a new one.

Each key has scopes: email:verify, bulk:write, finder:run, jobs:read, usage:read, account:read [Proposed].

Security-relevant events (create, revoke, failed auth) are written to AuditLog.

5.5 Validation, pagination, idempotency, versioning

Request schemas are validated by DRF serializers; unknown fields are rejected [Proposed].

Pagination: cursor-based with limit and cursor parameters [Proposed]; maximum page size is configurable.

Idempotency: POST creation endpoints accept an Idempotency-Key header; a repeated key from the same owner returns the original job [Proposed].

Versioning: URL path (/api/v1/). Breaking changes require /api/v2/. Documentation is generated by drf-spectacular.

5.6 Rate limiting

Per-key throttling using DRF throttling backed by Redis. Exceeded limits return HTTP 429 with a Retry-After header. Specific numeric limits are [Open] and must be derived from measured capacity; no number is promised here.

6.2 Pipeline

Normalize: trim, lowercase domain, preserve local part as given; IDN domain to ASCII form for DNS.

Syntax validation. Failure ends the pipeline.

Domain-level checks with caching in DomainRecord: DNS resolution, MX lookup, disposable, free-provider flags.

Address-level flags: role-based local part (e.g. info, support, sales; list maintained as data).

Decide whether SMTP probing is allowed (configuration, domain not on a do-not-probe list).

SMTP probe: connect to MX hosts in preference order, EHLO, MAIL FROM, RCPT TO the address; always QUIT without sending a message.

Catch-all probe: RCPT TO a random non-existent local part on the same domain (cached per domain).

Apply decision rules to produce status, reason codes and evidence level.

6.3 Statuses [Proposed definitions]

Status

Meaning

Deliverable

Syntax and domain checks pass, and a mailbox-level SMTP check accepted the address on a server that does not accept arbitrary recipients. Still not a delivery guarantee.

Undeliverable

Strong negative evidence: invalid syntax, nonexistent domain, no mail route, or a definitive recipient rejection.

Risky

Address may work but carries known uncertainty: catch-all domain, disposable provider, or similar.

Unknown

Evidence is insufficient or inconclusive (timeouts, temporary failures, blocked probing, probing not performed).

Rules 1 to 12 are evaluated in order and the first match gives the base status. 6.5 Retry and timeouts [Proposed]

DNS and SMTP operations use explicit timeouts; values are configuration, not hard-coded.

Temporary SMTP failures are retried with exponential backoff and a maximum attempt count, executed as Celery retries rather than blocking web requests.

Per-domain concurrency and probe rate limits prevent the platform from behaving like an abusive prober.

Results from domain-level checks are cached with an expiry in DomainRecord.

6.6 Result record

Each EmailVerification stores status, reason codes, an evidence object (what was checked and what each check returned), the evidence level (none, syntax, domain, mailbox) and the engine version, so results remain explainable and reproducible.

6.7 AI boundary [Confirmed]

No AI component participates in verification. Classification uses only technical evidence and the rules above.

6.8 Hosting prerequisite and fallback

Mailbox-level checks require outbound TCP port 25 from the probe host. Phase 3 begins with a capability spike on the intended host (Part 14).

If port 25 is unavailable, the engine runs in domain-level mode: syntax, DNS, MX, disposable and role flags only. In that mode no result may be Deliverable; results are Undeliverable (strong negative evidence), Risky (disposable) or Unknown with PROBE_UNAVAILABLE. The UI states this plainly (S-09).

The probe identity (HELO name, MAIL FROM, reverse DNS) must be a real, operator-controlled configuration (D-20). SMTP transcripts are not stored.

Part 7: Email Finder Engine

7.1 Source rules [Confirmed]

Only publicly accessible, legally permissible information. No authentication bypass, no CAPTCHA bypass, no restricted-page access, no paid or private email databases. Website terms, robots policies and privacy law are respected. Public visibility does not automatically mean unrestricted processing. [Validate] jurisdiction-specific legal review is required.

7.2 Safe fetching (applies to every outbound request)

Allow only http and https schemes; restrict ports to defaults (80, 443) unless configured [Proposed].

Normalize URL, extract host, resolve DNS ourselves.

Block loopback, private (RFC 1918), link-local (including the cloud metadata address 169.254.169.254), unique-local and other reserved IPv4 and IPv6 ranges.

Connect to the validated IP (pinning) to reduce DNS-rebinding risk.

Handle redirects manually with a maximum count and re-run all checks on each hop, including the final target.

Enforce connect and read timeouts, a total time budget, and a maximum response size; skip non-text content types.

No credentials, cookies or user headers are forwarded; a clear User-Agent identifying the crawler is used [Proposed].

7.3 Robots and limits [Proposed defaults, configurable]

Control

7.4 Company finder pipeline

Validate and normalize URL; extract domain.

Safety checks and reachability test.

Fetch robots.txt; build page queue starting with the homepage and prioritized links.

Fetch permitted pages within limits; record each in CrawlPage.

Parse HTML (BeautifulSoup4 with lxml). Extract emails from mailto: links and visible text via a conservative pattern.

Normalize (lowercase, strip punctuation and tracking parameters) and deduplicate per job.

Record source page and method (mailto_link or page_text) for each email.

Classify category (general, support, sales, careers, HR, management, press, other, unknown) from local part and page context; use unknown when evidence is weak.

Optionally send emails to the verification engine.

Persist results and set job status.

Obfuscated email formats (for example text written as name [at] domain) may be handled as an optional, clearly labeled method [Proposed]. Protected or script-hidden content is not decoded in ways that circumvent access controls.

7.5 Person finder pipeline (Both-Plus) [Confirmed]

Method A: profile URL

Validate the URL and check it belongs to a supported source type.

Check robots and access rules. If access is restricted or login-gated, return ACCESS_RESTRICTED. Do not attempt to bypass.

Retrieve only accessible content and extract name, title, company and associated domain where present.

Search permitted public company pages (Company Finder pipeline) for a publicly disclosed email for that person.

Record source; verify any discovered email; return structured result.

No claim is made that any professional platform allows automated crawling. Support for specific sources is decided per source after terms review [Validate]. Recommendation (D-05): do not fetch professional-network pages whose terms prohibit automated access; return an unsupported-source or access-restricted result and suggest the name + company method.

Method B: name + company

Validate input: full name, company name, optional domain, optional profile URL.

Identify the company domain from public information (or use the domain supplied).

Search permitted public company pages for a matching person and any explicit email.

Analyze company email patterns only when enough discovered emails exist to support a pattern.

Optionally generate an inferred candidate and label it inferred.

Verify candidates independently; return with sources and evidence.

Inference threshold: an inferred candidate may be generated only when the evidence rule approved in D-06 is met (recommended: at least two discovered emails on the same domain consistent with one pattern). Otherwise the result is Unknown or Not found, never a guessed address.

Result classification

State

Definition

Inferred

Generated from an identified company pattern; not published. Never presented as discovered.

Unknown

Not found

No reliable candidate; the email field is null.

7.6 Optional AI use

AI may help extract job titles or company descriptions from unstructured public text. It must not invent emails, must not declare deliverability, and its output is stored with a method label so it can be distinguished from deterministic extraction. The finder works with AI disabled.

7.7 Company and People Intelligence

Both modules read from the same extraction and source-tracking engine. Company Intelligence fields: name, website, domain, description, industry, public emails, phones, address, contact page, about page, social links, team page. People Intelligence fields: full name, title, company, domain, public profile, public business email, discovery source, verification result. Every field stores its source URL; a field with no evidence is null or Unknown.

7.8 Persistence and scheduling

Each finder run is a FinderJob executed by Celery. Page fetching is sequential per domain within limits. Jobs record status (queued, running, completed, failed, cancelled, access_restricted), counts and error codes. Retries are idempotent due to unique(job_id, url) and unique(job_id, email_normalized).

Part 8: Security and Privacy

8.1 Authentication and authorization

Passwords hashed with Argon2 [Proposed]; password reset via single-use, time-limited tokens; email verification required before use of finder or API [Proposed].

django-axes (or equivalent) for login throttling and lockout [Proposed].

Secure session cookies: Secure, HttpOnly, SameSite; session rotation on login; session listing and revocation in settings.

Optional Google OAuth: only when credentials are configured; never required.

Roles [Proposed]: Visitor (unauthenticated), User, Admin. Additional roles (for example Auditor) are an [Open] item.

Every query is filtered by owner. Object-level permission checks are tested (Part 12).

8.2 Web security

CSRF protection on all state-changing session requests.

XSS: template auto-escaping; no unsafe HTML rendering of crawled content; Content Security Policy and secure headers.

SQL injection: Django ORM and parameterized queries only.

HTTPS only in production with HSTS; secrets from environment variables only.

8.3 SSRF and crawler safety

See Part 7.2. SSRF protection is mandatory on every outbound fetch, including redirects. Crawler identity, robots handling and rate limits are part of abuse prevention toward third-party websites.

8.4 File upload security

Allow only .csv and .xlsx; validate extension, content type and file signature; enforce size and row limits.

Parse with csv and OpenPyXL in data-only mode; never execute formulas or macros; neutralize spreadsheet formula injection in exports (prefix cells starting with =, +, -, @).

Store uploads outside the web root with random names; delete after processing or per retention setting.

8.5 API key protection

See Part 5.2. Keys hashed at rest, shown once, scoped, revocable, never logged.

8.6 Abuse prevention

Per-user and per-key throttling and concurrency limits; job-count caps per user [Open: values].

Probe rate limits per target domain for SMTP and crawling.

Abuse monitoring dashboard for admins; ability to suspend accounts and keys.

Honest capacity messaging: no unlimited-throughput claims.

8.7 Privacy, retention and legal

Collect only business-relevant professional data; avoid unnecessary sensitive personal information.

User-controlled retention and deletion of history; account deletion behavior defined in Part 4.6.

Suppression and opt-out handling through SuppressionEntry; suppressed addresses are excluded from results [Proposed].

The platform does not claim legal compliance. [Validate] privacy and data-protection law (for example in each target jurisdiction), website terms and anti-spam rules require jurisdiction-specific legal review.

Backups are encrypted and access-controlled; deletion requests must account for backup expiry [Validate].

8.8 Admin access and audit

Admins can manage accounts, jobs and system settings. Viewing a user's private records requires a defined, logged authorization process (reason recorded in AuditLog). The exact approval workflow is an [Open] item. All admin actions and security events (login failures, key events, permission denials) are written to AuditLog.

8.9 Monitoring and secrets

Sentry is optional for error monitoring; configure to avoid sending personal data [Validate]. Logs must not contain passwords, full API keys, session tokens or full uploaded content.

Part 9: Rules

9.1 What to use

Django Templates, HTML, CSS, JavaScript for the UI. Django ORM for data access.

Deterministic Python for verification and extraction. Celery for anything slow or external.

The libraries listed as Mandatory in Part 3.6; Optional ones only when their stated need appears.

9.2 What to avoid

React, Next.js or any separate frontend project.

Microservices without a demonstrated requirement.

Mandatory paid verification APIs or private/paid email databases.

Any bypass of login, CAPTCHA or access restrictions.

Unverified claims: 100% accuracy, unlimited throughput, access to private profile data.

Redundant libraries and duplicate modules with overlapping responsibilities.

9.3 Coding conventions [Proposed]

PEP 8; type hints on public functions; docstrings on engine entry points.

Business logic in core/ and app services; views and serializers stay thin.

Settings split: base, development, production. No secrets in code.

Migrations reviewed; no raw SQL unless justified and parameterized.

9.4 AI boundaries [Confirmed]

AI is optional and disabled by default; platform must pass all core tests with AI off.

AI may help structure public page content only.

AI must never decide deliverability, invent emails or replace evidence rules.

AI-derived fields are labeled as such in stored data.

9.5 Error handling, data integrity, development rules

All errors use codes from Part 15; user messages never leak internals.

Jobs are idempotent; writes use transactions; unique constraints enforce deduplication.

Every discovered email stores source and method when available; discovered vs inferred is never mixed.

Every feature has a test and an acceptance criterion before it is considered done.

Implementation follows the phase order in Part 14; avoid unnecessary parallel development.

Never hardcode credentials.

11.6 Bulk verification

sequenceDiagram

  participant U as User

  participant W as Web/API

  participant DB as PostgreSQL

  participant Q as Redis/Celery

  participant K as Worker

  U->>W: Upload CSV/XLSX

  W->>W: Validate file, detect columns

  U->>W: Choose email column

  W->>DB: Create BulkJob, BulkRecords (normalized, deduplicated), BulkChunks

  W->>Q: Enqueue chunk tasks

  W-->>U: Job id

  K->>DB: Claim chunk (conditional update)

  K->>K: Verify records

  K->>DB: Save results + mark chunk done (one transaction)

  U->>W: Poll progress

  U->>W: Export CSV/XLSX

Pause/resume: supported by not enqueuing new chunks while paused [Proposed; confirm practicality]. Cancel: stops enqueueing and marks pending chunks cancelled.

Worker crash: chunks left running beyond a timeout are returned to queued by a Celery Beat sweeper; processing skips records already in a final state.

Duplicate job submission: detected by file hash plus column per owner; user is warned (DUPLICATE_BULK_JOB) and may proceed [Proposed].

11.8 API key creation and authentication

User opens API Management and names a key and scopes.

Server generates random key, stores prefix and hash, shows full key once, writes AuditLog.

Client sends Authorization: Api-Key header.

Server looks up by prefix, compares hash in constant time, checks status and scope, applies throttling, records usage.

Revoked or invalid keys return 401 and are logged.

11.9 API bulk processing

Same as 11.6 but created via POST /api/v1/email/verify/bulk; returns 202 and job id; results via /jobs/{id}/results; Idempotency-Key prevents duplicate jobs.

11.10 Search history and report export

User selects records; export task builds CSV or XLSX; file saved to storage; ExportRecord created; download link authorized by owner check and expiry.

11.11 Admin job monitoring

Admin views job and worker status. Access to a specific user's record contents requires the audited process in Part 8.8.

11.12 Failed task recovery

Task fails: retry with exponential backoff up to a limit; error code stored.

Retries exhausted: job marked failed or partially completed with failed chunks listed; user can retry failed chunks.

Redis unavailable: new jobs are rejected with SERVICE_UNAVAILABLE; running state is in PostgreSQL, so jobs resume when the broker returns.

Database unavailable: requests fail with SERVICE_UNAVAILABLE; workers retry connections; no result is acknowledged before commit.

Part 17: Limitations and Assumptions

17.1 Technical limitations [Limitation]

SMTP checks cannot prove mailbox existence or inbox delivery; catch-all, greylisting, provider blocking and outages can make results inconclusive.

Verification never reaches 100% accuracy.

Many professional platforms restrict automated access; such pages return ACCESS_RESTRICTED.

Public pages may not list emails; empty results are valid results.

JavaScript-rendered content may need Playwright, which is deferred.

Capacity is finite; throttling and queues manage load.

Many cloud hosts block outbound port 25, so mailbox-level probing may be unavailable on them (Part 22.2).

17.2 Assumptions [Assumption]

Hosting permitting outbound port 25 is no longer assumed; see Part 22.2 and D-02.

Initial scale fits a single-host or small multi-worker deployment.

Email address lists for disposable/free/role detection are maintained as data and updated periodically.

Part 22: Validation of SMTP, Hosting, Security and Legal Considerations

22.1 SMTP verification limitations (validated against the design)

Mailbox probing needs outbound TCP port 25 from the probing host to arbitrary mail servers. Cloud hosts commonly restrict this to fight spam.

A server may accept every recipient (catch-all), defer with temporary errors (greylisting), hide mailbox existence, or block the prober's IP. These cases produce Risky or Unknown, never Deliverable.

Probing from one IP at volume risks that IP being blocklisted; this affects result quality for every user. Rate limits per mail host, a proper reverse DNS name and a real HELO name are required (D-20).

A successful RCPT answer does not prove inbox delivery.

22.4 Security checklist (to verify in Phase 11)

SSRF: scheme and port allow-list, DNS resolution then block of private, loopback, link-local (including cloud metadata 169.254.169.254) and reserved IPv4 and IPv6 ranges, IP pinning, re-validation on each redirect, timeouts, size caps.

Authentication: Argon2, lockout, secure cookies, session rotation, CSRF, password reset tokens single-use and expiring.

Authorization: owner filters on every query; object-level tests; scoped API keys; admin actions audited.

API keys: random, hashed, shown once, revocable, never logged.

Uploads: extension, content and signature checks, size and row limits, no formula execution, export neutralization of formula-leading cells, files outside web root.

Output safety: escape all crawled text; never render crawled HTML.

Logging: no passwords, keys, tokens or SMTP transcripts.

Dependencies: pip-audit and Bandit in CI; Docker image minimal and non-root.

Secrets only from environment or a secret store; .env never committed.

Backups encrypted; restore tested.

Part 23: AI Coding Agent Instructions

These rules apply to any AI coding agent or developer implementing this specification. They are part of the specification and are binding.

23.1 Operating principles

Implement only the phase currently authorized. Never start a later phase.

Never invent a product decision. If a decision is missing or listed in Part 21 as unapproved, stop and ask the owner with the options.

Never invent library behavior, API fields or provider capabilities. If unsure, read the official documentation or write a small test to confirm, and record the finding.

Prefer the simplest design that meets the specification. Do not add libraries, apps, models or endpoints that are not specified; propose them instead.

Core finder and verifier must work with AI disabled. AI must never decide deliverability or invent an email.

Every result must keep evidence: source and method for discovered emails, reason codes and evidence level for verification.

Never bypass authentication, CAPTCHA, robots rules or access restrictions, and never fetch a URL without the SSRF guard.

Keep documentation in sync: when behavior changes, update the specification and the changelog in the same change.

23.2 Repository and file structure standards

Follow Part 3.9. Additional rules:

Business logic lives in core/ or in each app's services.py; views, serializers and templates stay thin.

Each app has: models.py, services.py, views.py, urls.py, serializers.py (if API), tasks.py (if Celery), tests under tests/<app>/.

Settings split into base, development and production; no environment-specific values in code.

Templates under templates/<area>/; reusable parts under templates/components/.

One migration per logical change; never edit applied migrations.

Names: snake_case modules and functions, PascalCase classes, UPPER_CASE constants; reason codes and error codes are constants defined once in core and imported everywhere.

No dead code, no commented-out blocks, no TODO without an issue reference.

23.3 Implementation rules

Type hints on all public functions; docstring on every engine entry point stating inputs, outputs and what it cannot establish.

All outbound network access goes through one safe-fetch module (HTTP) or one SMTP client module; no other module opens sockets.

All time limits, sizes and counts come from configuration with documented defaults (Part 21.1 once approved).

Celery tasks must be idempotent, accept primary keys not objects, set time limits, retry only on retryable errors with exponential backoff, and update job status in the database.

Database writes that must succeed together use transactions; uniqueness is enforced by constraints, not only by code.

Every query on user data filters by owner; add a test per endpoint proving another user gets 404.

Never log secrets, tokens, API keys, passwords, full uploads or SMTP transcripts.

Use constants for status and reason codes exactly as defined in Part 6 and Part 15.

23.4 Test-first workflow per task

Read the phase section, the relevant workflow (Part 11), screen (Part 10), API (Part 5) and errors (Part 15).

Write failing tests from the acceptance criteria.

Implement the minimum to pass.

Run the full test suite, linters, Bandit and pip-audit.

Complete the self-review checklist (23.6).

Update docs and changelog; report what was done, what was not done and any questions.

23.5 Specific technical rules

CSV uploads: decode as UTF-8 with or without BOM; detect delimiter among comma, semicolon and tab; header row detection; reject files that cannot be parsed with INVALID_CSV.

XLSX uploads: read-only, data-only mode; use the first sheet by default and let the user choose another sheet [Proposed]; ignore formulas; reject macros files.

Export: neutralize cells beginning with =, +, - or @.

Email normalization: trim whitespace; lowercase the domain; convert IDN domain to ASCII for DNS; keep original input for display.

Never treat candidate generation as evidence; store origin as discovered or inferred and never change it.

SMTP client: connect with timeouts, EHLO with configured name, MAIL FROM with configured address, RCPT TO, then QUIT; never send DATA.

If mailbox probing is unavailable, return the documented domain-level result and PROBE_UNAVAILABLE note, not a guess.
